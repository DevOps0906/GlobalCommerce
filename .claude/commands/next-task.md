팀장(이 세션)으로 진행한다. 팀 구성과 위임 기준은 `develop/MULTI_AGENT.md`, 작업 정본은 `products/06_AGENT_PLAN.md`.

1. 작업을 고른다. `$ARGUMENTS`에 작업 번호(예: `007` 또는 `GC-06-007`)가 있으면 그 작업을 고른다. 없으면
   `tasks/README.md` 진행 현황 표에서 상태가 `대기`이고 06장 2절 "의존"이 모두 `완료`인 것 중 06장 3절 웨이브 순서(W0 → W7, 웨이브 안 `→` 순서)로 가장 앞인 작업을 고른다.
   - 화면 작업은 GC-06-004 완료 뒤에만 고른다 (06장 1절).
   - 현재 릴리스 밖(R2 · R3) 작업은 사용자가 지정하지 않으면 고르지 않는다. 036 · 044 는 `[DECISION] G1 통과` · `[DECISION] G2 통과`가 기록된 뒤에만 고른다.
2. `tasks/task-###.md`가 없으면 `tasks/TEMPLATE.md`를 복사해 만들고, 06장 2절 해당 행(웨이브 · 릴리스 · 규모 · 소유 경로 · 의존 · 담당 · 수용 기준 · 기능 ID)을 옮긴다.
   있으면 읽고, 로그의 `[DECISION]` · `[REQUEST]`(이 작업 소유 경로로 들어온 요청 포함, `grep -n "\[REQUEST\] GC-06-###" tasks/*.md`)를 먼저 확인한다.
3. "참고 문서"는 **작업에 필요한 장만** 읽는다. 디자인 캔버스 · 스펙에서 값만 뽑는 일(화면 문구 · 수치 · 마켓 필드 표)은 사원(sub-agent-2)에게 맡긴다.
   열린 결정(`products/00_DECISIONS.md` 4절 O-##)에 걸리면 기본안을 적고 사용자에게 확인할 항목으로 올린다.
4. 구현 계획을 짧게 정리한다: 바꿀 파일(소유 경로 안), 순서, 맡길 에이전트 · 호출 모델(`develop/MULTI_AGENT.md` 3.3), 하위 지시, 확인 방법(수용 기준별).
   - 06장 담당 모델이 Fable 이면 고문(advisor) 설계 검토 1회 → plan-challenger 순서로 착수 전 검증한다 (`develop/MULTI_AGENT.md` 4장 5번).
   - 06장 검증 열에 plan-challenger 가 있거나, 규모 L 이거나, 결제(Toss) · 크레딧 차감 · 권한 · RLS · DB 스키마 · 마켓 API 키 암호화 · 마켓 업로드 · AI 키 · 프롬프트 · SNS 토큰 · 잡 큐 · 실행 엔진을 건드리면
     **plan-challenger**로 계획을 먼저 검증하고 결과(판정)를 함께 보여 준다.
5. 계획을 사용자에게 보여 주고 승인을 받는다. 승인 내용과 판단은 task 로그에 `[PLAN]` · `[DECISION]`으로 남기고, `tasks/README.md` 상태를 `진행`으로 바꾼다.
6. 승인 후 위임한다. 06장 담당 에이전트가 기본이고, 하위 지시는 `develop/MULTI_AGENT.md` 3.1 기본 영역을 따른다
   (화면 · 컴포넌트 · 셸은 대리, 서버 · 인증 · 결제는 nextjs-expert, DB 는 supabase-expert, 워커 · `packages/*`는 worker-expert, 문구 상수 · 체크리스트는 사원).
   위임은 `[DELEGATE]`로 남긴다. 한 줄 수정처럼 위임 비용이 더 큰 일은 팀장이 직접 한다. "안 할 것"과 소유 경로 밖은 누구도 건드리지 않는다 — 필요하면 `[REQUEST]`.
7. 변경 후 **review-expert**로 리뷰하고, 06장 검증 열의 에이전트를 형제로 함께 부른다. 06장에 없더라도 경계 · 계약 변경이면 contract-reviewer,
   인증 · 결제 · 크레딧 · 키 · 토큰 · RLS · 외부 fetch · 파일 업로드 · AI 프롬프트 · 개인정보 변경이면 security-auditor, 마이그레이션이면 둘 다 붙인다.
   "검증 근거 없음"이 나오면 test-writer 로 테스트를 만들고 다시 리뷰한다. 리뷰 동안 `tasks/README.md` 상태는 `리뷰`, 판정은 task 로그에 `[REVIEW]`로 남긴다.
8. 🔴 지적은 해당 에이전트에게 돌려 고친다. 같은 문제로 2회 이상 막히면 고문(advisor)에게 자문한다.
9. 완료 조건(수용 기준)을 하나씩 확인하고 결과를 표로 보고한다 (누가 무엇을 했는지 포함). task 파일의 "완료 보고" 표를 채우고 `[DONE]`을 남긴다.
10. `tasks/README.md` 상태를 `완료`로 바꾸고, 루트 `CLAUDE.md` 4장 형식으로 커밋한다 (사용자가 커밋을 막아 두었으면 커밋하지 않고 메시지 초안만 제시).
